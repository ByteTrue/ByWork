# 写成人话、去推导泄露与语义自检

适用：写 `bywork/` 记录、提交说明和给用户的回复。

## 1. 写成人话

- **黑话和抽象比喻**：不造「门面」「收口」「水位」「底座」「抓手」「赋能」「心智」「闭环」这类词；直接说具体的文件、函数、命令或行为。
- **公文腔和翻译腔**：不写「进行…处理」「实现…功能」「予以」「旨在」「通过…的方式」；直接写动词，「改 X」「删 Y」「用 Z 校验」。
- **空洞形容**：不写「更加清晰」「显著提升」「全面覆盖」「极简优雅」「有机结合」；写具体改了哪几处、少了多少行、拦住了什么错。
- **自我夸耀和客服套话**：不写「完美解决」「彻底根除」「很高兴为您」「好的，没问题」；直接给结论和证据。
- **连接词堆砌**：少用「首先…其次…最后…此外…综上所述」「值得注意的是」「需要指出的是」；能分行就不串成一段，能删掉连接词意思不变就删掉。
- **模糊指代**：少写「该模块」「上述逻辑」「相关配置」「此问题」；指名道姓写路径和符号名。
- **绕弯子的被动句**：不写「该字段由脚本进行更新」；写「`bw.py` 更新这个字段」。
- **把简单判断包装成理论**：不把「先读文件再改」写成「遵循先验感知契约」；怎么做的就怎么写。
- **加粗成瘾**：正文句子里不靠满篇 `**加粗**` 划重点；只有列表项开头的标签、表头或确需一眼扫到的关键字才加粗，普通叙述整段不加粗。
- **Emoji 和装饰符号**：文档、汇报、提交说明里不用 emoji 或花哨符号点缀。
- **机械排比和凑三点**：有几件事写几件事，不为对称硬凑三条，也不把一句话能讲清的事拆成三层列表。
- **先铺垫再给结论**：回答问题或汇报结果时，第一句先给结论或当前状态，再摆证据和细节，不先讲思考过程。
- **用反面定义正面**：能直接说「做什么」就别绕成「不是 A，也不是 B，而是 C」；只在对方确实容易踩进某个坑时才点名「不要 X」。
- **名词套名词**：不写「完成状态流转逻辑的收敛」；写「把状态改成三条并由脚本更新」。

## 2. 行文原则与按位置自检（Prose Standard）

- **只写产物自己说不清的**：行为边界、失败处理、时序、所有权、后果与取舍。不复述代码字面内容或推导过程；能编进类型、接口或报错的约束，不只写在文档里。
- **保留会改变判断的完整命题**：删字时保留适用条件、义务强度、否定保证、例外与后果；只写本条实际涉及的内容，不为凑清单补造约束。
- **一个事实只在一处讲透**：其余地方用相对链接指过去，不把同一规则抄得到处都是。
- **按位置核查**：
  - **`## 决策` / `## 收益和代价`**：区分边界、拒绝条件、副作用、所有权、时序、取消与持久化是否说清。
  - **自由节（拓扑/契约/结构）**：讲清职责、依赖与非显而易见的选择及指向。
  - **`## 备选方案` / `## 收益和代价`**：同时写代价与收益，点名放弃的能力与重新引入条件。
  - **验证说明**：只解释「为何这样验证」（夹具/断言/真实入口的必要性），不写测试走读流水账。

## 3. 去推导泄露自检（Trim CoT Leakage）

对每段文字自问：**只有当时的会话/PR/草稿才看得懂吗？现在的读者只看仓库能独立验证吗？** 不能则重述为仓库当前视角，删去会话痕迹。

**8 类常见泄露（命中即改）**：
1. **死引用**：`(decision 7)` / `(audit C2)` / `§N` / `plan §1.4` → 改为对已提交记录或文档的具名相对路径链接；无对应文件则删引用、直接重述事实。
2. **栈/PR 视角**：`后续 PR` / `本 PR 新增` / `上一 commit` → 改为已落地的机制或扩展点；未做事项用 `TODO`、issue 引用或收进延迟小节。
3. **变更叙事**：`以前是` / `不再` / `旧 X` / `现在改为` → `implemented/` 一律改为**现在时**；防回归理由用现在时反事实「若无 X 则会导致 Y」。
4. **评审编排**：`评审时否掉` / `用户确认` / `第二轮修改` → 只留决定与客观理由，删掉谁说的、第几轮说的。
5. **自证正确**：`这样转是安全的，因为…` → 改为使之安全的不变量（invariant），或直接删（代码已自明时）。
6. **过程复述**：`先 X 再 Y` / `测试走读` → 删掉探索过程，只留非显然的契约。
7. **含糊与占位**：`应该够了` / `大概可行` → 升为明确的边界条件或 `TODO/FIXME`。
8. **语言串台**：中英混杂的半截工作语言片段 → 统一译为准确的中文表述（技术术语、命令与标识符照原样保留）。

**不算泄露（应当保留）**：issue/PR 编号引用、带具名原因的 suppression 理由、现在时反事实、带实测值的边界、运行时新旧状态对比、已提交文档的章节号。

## 4. 四个删过头警示（Overcorrection Traps）

删减之前先把段落里的核心命题列全，严防四个「删过头」的坑：
1. **把必须/禁止的义务删成「可以这样」的背书**——刚性约束变成了可选项。
2. **把「计划中/考虑过」的假设删成已落地事实**——把 `proposed` 当成了 `implemented`。
3. **删掉一句真事实，只因为它读起来像过程叙述**——应改写为现在时事实，而非连事实一起抹掉。
4. **丢掉承重溯源**——把 `实测：512 嵌套 ≈ 0.15s` 里的 `实测`、来源标注与具体量级删掉，结论就没根了。

## 5. 写完记录后的逐节语义自检（Quality Gate）

脚本管结构，以下清单管意思（写完记录后自检，有缺口先修再落盘）：
- [ ] **动手前**：能通过去中心化检索 4 法或读仓库自己查到的事实，绝不抛给用户问；只有取舍和拍板才占用用户时间。
- [ ] **`## 问题`**：删掉 `## 决策` 再读一遍，问题与触发条件是否依然独立成立？
- [ ] **`## 决策` / `## 提案`**：是否具体到能行动和核对？理由是否写清了「X vs Y 为何选 X」？
- [ ] **`## 备选方案`**：是否忠实记录了真实权衡过的备选，或说明没有独立备选？每个被否项是否**先写了它最强的论据**，再写具体驱动条件下的放弃原因（无稻草人）？
- [ ] **验证**：结论是否能回到实际证据？已覆盖、未覆盖和仍需验证的范围是否分清？替代旧记录时有没有漏掉验证义务或具名缺口？
- [ ] **`## 收益和代价`**：代价和收益是否都写了（什么变难了、维护成本是什么）？若是简化，是否写明了已知上限与何时重访？是否去掉了无基线的相对量词？
