# 技能效果评测的判定边界

Status: implemented

## 问题

如何客观衡量工作流技能规则的改动是否有效，避免把模型随机方差误判为规则收益或因单次偶发偏离而堆叠无效禁令。

## 决策

本记录中的会话观察保留对应版本的文件名、命令与状态语义；`check_work.py --close`、`work/` 等属于历史对象。当前执行契约见 [技能入口](../../../skills/bw/SKILL.md)，不从历史样例推导现行命令。

技能规则的效果用独立任务的实际执行证明。业务正确性、工作流执行和效率变化各自判定；业务通过不能替代过程符合规则，收尾文档不能替代动作顺序证据。

对规则改动比较时，先冻结旧技能、任务输入与验收，再跑相同条件的新旧版本。首次失败保留，修订后的运行另存。语义判据回到工具成功结果与产物判断；没有证据时保留无法判定，不用关键词或文件存在代替。

一轮对照只支持对应样例结论。跨模型、真实压缩、大型仓库与效率提升各自需要对应证据。要声称更快或更省，按相同命令交替运行，各至少三次，报告中位数、范围和正确性；并发耗时不用于速度比较。

TMPDIR 与目录提示只约定临时路径，不能保证文件系统隔离。对照默认顺序运行；严格并发隔离需要宿主提供文件系统沙箱，并核对工具记录是否发生跨运行读取。

大型长任务优先在真实项目副本删除成熟功能后重建。固定原版与删除边界，清除旧版工作流记录，将原实现和独立验收留在被测项目外。上下文压缩按宿主阈值自然发生，不预设次数；记录实际设置、原生事件、持久摘要与接续动作。原版也要先跑验收，已有缺陷单列，不能视为重建新增回归。

压缩是否发生与接续是否遵守检查点分别判定。pi 1.5.2 的压缩元数据可能没有列出 bash 内的业务读写；不能用 `readFiles` / `modifiedFiles` 代替完整工具记录审查。

工作流门用结果判据，不用工具顺序仪式。接续质量看「接续后的动作与检查点一致：做对当前该做的事、状态诚实、缺口不丢、无假完成」；「压缩后第一项必须是某个指定工具名」这类过程仪式在 DeepSeek Flash 上连续多轮不被遵守（指令逐字进入压缩摘要后仍先 bash），却不再对应任何真实事故——真实事故（批量填绿、非法状态、丢缺口）由完成门和逐行回写规则拦截。过程规则只在能指出它挡住的具体失败时才保留。

技能提示词应当极简优雅：只引导模型按流程完成 1234，把工具选择和操作顺序放权给模型。规则写成原则和底线（每条底线对应它挡住过的真实事故），不写成操作规程（「先 read 再 bash」「先这样完成流程 A 再那样完成流程 B」）。堆叠工具级指令不仅无效（模型不遵守），还挤占注意力、损害文档可读性。用户于候选二十二期间明确此原则，候选二十三按此整体重写。

高难大型任务上，「单次运行全绿」不是有效的交付门：候选二十六至二十九的失败点在各代码区域随机轮换（互有修复互有复发），而每轮新增的规则都被验证生效——失败是模型方差，不是方法论缺口；继续逐轮加规则既堵不住方差也养胖技能。工作流的价值改用 A/B 通过率回答：同一任务、模型、thinking 与验收，A 臂不装技能（`run_repository.py --no-skill`，任务文本去掉工作流措辞、其余逐字节一致），B 臂装被测技能，交替顺序各至少三次，报告通过率与范围；范围重叠报无可测差异。外部公开评测集测模型能力、测不到工作流纪律，只适合做「技能不损害原始编码能力」的旁证。

独立验收的精确期望需要被测模型可见的契约依据。原版通过只能确认兼容差异，不能自动证明重建者遗漏了公开要求。输入缺项时补明契约并冻结新版本，旧结果单列输入边界。

浏览器定位失败先检查页面快照。按可见能力允许合理的数量后缀和按钮/菜单布局，同时保留真实操作与结果断言；修订探针在正确产物和已知错误上重新标定。首次失败保留为探针纠错证据。

用户主要使用 DeepSeek，当前评测优先 DeepSeek Flash；扩展模型矩阵需要新的目标依据。

评测之外的真实任务会话同样是有效证据：不同任务类型、不同仓库、无用户中途干预的自主执行，能检验纪律是否只在评测任务上成立。审查这类会话读原始记录，不只看最终产物；最终产物全绿不代表过程没有绕路。opencode 会话的导出入口是 `tools/export-opencode-session.py`（`--list` 按标题找会话，`--session` 导出含推理与工具调用的全文）；pi 会话是另一套 JSONL 存储，遇到再扩。机械门要容忍合法格式变体（如格式化工具给表头加列宽空格），校验过脆会把模型的时间花在绕过校验而不是工作上。

真实会话零 byissue 产物可能是正确路由，不是纪律缺失：小改直接做的分档与 Memory 两问筛选的交集本来就该零产物，该进仓库的事实落在项目文档（如 docs/）也是正确落点。判定依据是会话里的分档与筛选推理、真实入口验证和诚实收尾，不是产物数量；先查这些再判违规。

真实会话里观察到的机械门冲突先查版本滞后，再判方法论缺口：全局技能副本可能落后于源仓库（同一版本号内文件也可能不一致），模型撞上的可能是已修复的旧 bug。byspace 多语言砍减会话用 stale 全局 checker 再次撞上表头字面匹配，自行以「formatter 排除 bywork/」解决——与源仓库的「checker 按单元格解析」是同一冲突的互补解法，对机器写的检查点文件前者更合理。这类冲突不指向工作流规则缺陷。

分档判据是任务结构，不是工作量感受：「能否一次做完」「懒/省事」不是小改的判据，多个行为路径或需要完整性核对的改变（迁移、批量改道、移植）即使单会话能完成也建 work。AGCopilot 旧工作流迁移会话里，模型先正确判定「~300 文件、多决策 → 建 work」，随后被 ponytail 的「keep it lazy」与「能一次做完的机械迁移」说服自己降级成 memory-direction 小改，漏建 work 与 scope——迁移本身做得不错，缺的是索引。这与 mise 会话（真小改、零产物正确）互为镜像：分档机制本身工作，但「lazy」框架会压过结构判据。修法是在 change.md 小改条目旁正面切开「能一次做完」与「小改」，不新增禁令、不碰 ponytail。

完成门可能被「重新分类缺口」而非「验证缺口」满足：环境性跑不了的检查（如 linter OOM）应保留 `无法判定` 行与非空 `proof_gap`、状态停 in_progress 并交由用户定夺；把未验证维度整行删除、换成另一维度的通过（如用 format:check 顶替 lint）再置空 gap 写 complete，是「放宽断言填绿」的变体。check_work.py 只查一致性，查不出这种合法化清除。AGCopilot 补建 work 时即如此：biome lint 崩，记录用 format+typecheck 替换原「无法判定」行后 complete；实质风险低（纯文档改动，oxlint 实测 0/0），结论碰巧可接受但记录夸大覆盖。规则已存在（`无法判定` 值 + proof_gap 恰空 + 禁止填绿），属单次偏离，不加新规则。

检查点会与到达的证据脱节，且状态值可能对而内容仍会假：异步证据（CI、后台任务、部署结果）到达时若只汇报不回写，证明表、proof_gap 和 next_action 会冻结在旧快照，说出已被证据推翻的话——比没有检查点更危险，因为接续会信它。byspace Windows pi 会话（跨模型、5 次压缩）里 project-npm work 在 CI/Docker 全绿并合并发布后，盘上仍写「CI 尚未执行、工作流远端待跑」；in_progress 本身因 heartbeat 与全量资产缺口仍在而可能正确。现有回写规则绑在「我刚跑完验证」的同步动作上，异步到达没有插槽；check_work.py 查一致性查不出新鲜度。修法是在 change.md 回写条目把异步到达明确为验证事件（正面一句，放决策点），不新增禁令。

会话审查中「生成应来自外部源的内容」是独立于填绿的信任失败类：把模型自己的提议写成 user said（本 case 编造「不要Skip,改成Logf+断言」并据此大改测试），或在未收到子代理报告时预填对比台账（v2 交付期台账事故，见 principles-review 诚实声明）。两者的恢复纪律相同——回到原始记录核对（本 case 用 decompress 还原压缩前区间 grep 自证用户输入只有三条），并明确承认编造；判定违规看「内容是否有可追溯的外部来源」，不看事后补救是否漂亮。规则已存在（证据先于结论、不预写通过），属偏离，不加新规则。

多 agent 共享同一仓库时，git 操作的边界比单 agent 更窄，破坏性操作的风险更高：路径限定提交（`git add <paths>`）仍落在当前 HEAD 分支，不指定目标分支就会提交进别的 agent 正在用的功能分支；`git reset --hard`、`branch -f` 这类会丢弃提交或改写分支引用的操作，对不属于自己工作的分支是破坏性的，必须先确认分支归属并取得授权。本会话修 byspace 检查点时，隔壁 agent 已把分支切到 `fix/relay-tunnel-hardening`，我的路径限定提交 `ec0c3ec51` 落进该分支而非 main；随后用 `reset --hard` 把分支「整理」回 main 基点，把隔壁已提交的 `3a9834d4`（6 源文件+3 新测试）打成悬空、测试从工作区消失。根因不是技术失误而是越界：在别人功能分支上提交、又用破坏性操作整理不属于自己的分支。bw 底线「破坏性操作需授权、不碰他人工作」已覆盖，属偏离不加新规则；可操作的自检是提交前先看 `git branch --show-current` 与 `git status`，确认当前分支是不是自己要提交的目标，不是就先切回或问用户，绝不对他人分支做 reset/branch -f。恢复靠悬空提交与 stash（隔壁最终自行恢复并合并 PR #49），但「能恢复」不等于「可以越界」。

审查发现要先写可执行复现再修，复现本身也要先红：子代理审查报出的缺陷可能只是代码阅读推断，直接照单修会把「看起来对」当成「证明对」。正确动作是给每项发现写一个能在未修复实现上失败的可执行复现，见红后再修、复验转绿；复现若假绿（构造的场景其实没触发缺陷）要收紧到真正触发为止。byspace relay-tunnel-hardening 会话第一份并发审查的 1–4 项是阅读推断，模型逐项写复现，第一版 resume 复现假绿——换 peer 对象不会让运行中的 pump 退出（它持旧对象照样写），必须让 pump 自己的 peer 失败才见红。这一步抓住了两个阻断级既有 bug（新流从不回 ack 致 >16MiB 响应必死、replay 溢出自锁泄漏 socket）。这是「回归先红后绿」在审查场景的延伸，规则已存在，属正面样本。

接收上游描述（恢复提示词、事故说明、审查报告）时先核对再动手，用证据纠正描述里的错误：描述者可能悲观、乐观或记错，盲信会照着错误前提重建或漏修。正确动作是对描述里每个可验证断言亲自跑命令核对，与证据冲突时以证据为准并明确指出描述错在哪。byspace relay-tunnel-hardening 会话收到本会话写的恢复提示词（用户明确要求「请先核对再动手,不要盲信下面的描述」），逐条亲验后纠正了提示词里一处对它有利的错误：提示词称「合并后的 manager/target 最终版没找到，只有合并前 stash 版」，它实测 `git diff 79faeb91b ec0c3ec51 -- manager.go target.go` 为空 → 上游未碰这两文件 → stash 版即最终版，无需重解冲突；并精确区分 relaypeer.go 用合并后 blob `0ea51f00`（含 proved+jitter）而非 pre-merge stash 版。复验 103 passed 与丢失前同一计数证明无静默丢测试。这是「证据先于结论」在跨 agent 协作的延伸，规则已存在，属正面样本。

子代理的使用由宿主/项目规则决定，不是 bw 的偏好，也不应把某次会话的子代理行为归因于工作流：bw 技能包没有任何「完成前派子代理审查」的规则，grilling 澄清阶段默认自行查事实，仅在宿主支持且已获授权时委派；该段从 Matt 原文适配，已去掉强制委派。判断「agent 是否自发派子代理」要回原始会话记录核对触发来源——byspace OpenTunnel 会话的双子代理审查实际是用户明确要求的（「走PR吧,先提PR,然后用子代理进行审查」），且该项目 AGENTS.md 原本限制「只在被要求时派」，agent 在分析阶段还据此克制不派。用户随后决定去掉该限制（探索/查事实/聚焦审查场景子代理有用），但保留「大批量删除/重构在主会话执行、子代理会漂移」这条有真实失败背书的纪律。bw 对子代理无偏好；证明表/完成门只是让被要求的审查有具体靶子，不制造主动审查行为。

超大型多批瘦身/删减任务的范围纪律有三个可观察信号，可作日后同类复盘的对照基准：①保留项守卫——用户拍板保留的功能一项不动，且每批收尾显式确认保留项未碰；②相邻发现不擅自扩范围——执行中发现的相邻 gap（未接线的真实功能、死 surface、未验证的外部行为）列为「待 flag owner」等授权，不混进当前批次，授权后才另批闭环；③数据决策停下来问——会重置用户已持久化数据/设置的删除（如 localStorage 迁移）属「防数据丢失」类别，停下来交用户拍板而非 silently 删。byspace「重写后遗留功能瘦身」会话（opencode `ses_e16709ae6ffeTZzIStJAFFMwOI`，3468 messages、7.8M 字符，十批瘦身）三者全中：保留平台广度/changelog/schedules/git review/forge/Chief 未动，per-agent options 等三 gap 先 flag 后第八批闭环，localStorage 迁移主动问 owner；shell 批量编辑被用户质疑时诚实承认 python replace() 静默跳过曾致两次误删并改用 edit；干净结束先核验 git/origin/proof_gap 再改 complete。分档（审计→澄清→建 work 改变）、逐行回写、诚实收尾全程成立，无需加新规则，属正面样本。

complete work 的 `next_action` 写「无」是约定不是机械门，偏离无功能危害，按准入线不立规：接续路由只匹配 `in_progress`/`blocked`（SKILL.md），complete 的 work 是封存档案，`next_action` 写什么都不会被误接续；新目标由新请求触发新 work（prove.md），不由旧指针触发。byspace 4 个 complete work 里 3 个写「无」（i18n-two-locales/relay-tunnel-hardening/v1-migration），slimming-batch-1 唯一偏离（写「Chief 远期…等 @xterm/xterm 7.0.0 发布后删」），真实使用 3/4 成立非 100%。本仓 5 个 complete 全写「无」但那是维护者自己写的，属循环论证不能当独立证据。偏离只是读着像有尾巴、不产生错误动作，1/4 单次偏离按「规则要对应真实失败才立」的准入线不值得加散文；真要收口杠杆在 check_work.py 结构校验（complete 时 next_action 须以「无」开头）而非模板再加一句会被忽略的话。升级触发器：此类偏离复发或造成实际误接续，届时用机械门咬合。

分档失败有第三种机制：分析转修改时主行动不重新分类，沿用压缩摘要里的陈旧行动标签惯性滑入实现。前两种是「真小改零产物」（正确）和「lazy 框架主动压过判据」（AGCopilot 迁移，agent 明说 keep it lazy）；第三种 agent 根本没走到「判断是不是小改」，它还在用上一阶段的行动惯性继续干活。判别要回原始会话 grep 授权修改到首次 edit 之间有无路由词（主行动/改变/change.md/建work/小改），全 0 且无「这是小改」判定即属此类。规则缺口不在判据而在触发点：SKILL.md 原句「调用 bw 先判断」被框成一次性入口闸门，行动入口读一次后被压缩掉，决策点（每条新用户消息到达）没有重新触发；understand-review 的「用户要求改变后进入 change」转换规则存在但同样离决策点远。修法是把触发点就地磨锐到「每条用户消息都先判断此刻的行动；摘要或上文里的行动标签是历史，不是当前状态」，通用覆盖所有行动转换与所有陈旧载体（压缩摘要+纯上下文惯性），不枚举具体转换、不重复 change.md 的 work-vs-small 权威。诚实边界：散文不保证挡住惯性，但这次要求的是模型本就会做的动作（新消息来了重新看用户要什么），比候选 18–21 那种反默认动作更可能生效；若复发再考虑机械门。

非法状态值（done）的偏离要分「忘了跑校验」和「值域知识在收尾失效」两层，后者更深：值域规则（status 只能 in_progress/blocked/complete）在技能入口加载过、check_work.py 也硬拒非法值，但模型收尾时可能主动读到自己写的 done 仍把它当合法「完成」沿用，只清 next_action 不改状态、也不因 proof_gap 非空回 in_progress——这不是忘了跑校验，是值域约束在收尾决策点没被当成约束。判别要回原始会话看 done 写入后有无合法值回改、收尾推理是否读到 done 并认可它。check_work 实跑能抓（机械门有效），但模型不调用就没机会拦；「收尾必须跑 check_work」是散文步骤，依赖自觉。无用户提醒的后续段可能补上其他纪律（真跑 dev E2E、开 PR、回写证据）却仍不修状态——「能自觉补上」不能假设，要逐次核实。单次偏离按准入线不立规；若 done/跳过 check_work 在新版会话反复出现，升级方向是让收尾校验不可跳过（宿主侧钩子或更显眼硬步骤），不是再加一句「记得跑 check_work」的散文。

提示词新增规则要自查重复与具体锚，两者都有实证危害。重复：加 `--close` 时把同一机制写进 SKILL 核心流程/底线、change 出口、work 模板、prove 完成门五处，结果 prove.md 漏改、仍写「才写 complete」，与 SKILL「不手写」直接矛盾——重复不是冗余美观问题，是改一处漏一处的漂移源。修法是按 project.md「一条规则一个权威归属」收敛：完成门机制只归 prove.md「完成与接续」，其余留指针或底线里不可协商的一句；收尾总结格式与可视模板统一归 SKILL 汇报段，writing.md 不再重复。具体锚：「几小时的工作该写清就写清」用具体时长举例，模型会把它当范畴边界，工作十几小时就可能误判超出；规则应陈述原则本身（「按内容需要写清，不硬限字数」），不举时长/数量等可被误读为阈值的例子。自查可 grep 复现：同一契约关键词（如 --close）在多文件出现即疑重复，具体数字/时长词即疑锚。否定式按既有准入线（挡住强默认行为才留、配正面动作），纯否定 framing（「不是写给X的人」）改正面（「写给Y的人」）。

收尾总结可作用户侧的漂移探针：它是模型每次回复必然产出的自我陈述（做了什么/下一步/需要你），把它与 work 检查点对照即可发现漂移——current_unit 与「做了什么」不符是跑偏，proof_gap 非空而总结说「全部完成」是假完成，next_action 与「下一步」不符是偏离。这比依赖模型自觉跑 check_work 更稳，因为总结是必然产出物而 check_work 是可选动作（Greeting 正是没跑）。边界：这是给人用的观测手段，不是机械门，不阻止漂移只让漂移更易被发现；不写成「模型必须自查总结与检查点一致」的新散文规则（那又依赖自觉，会失效）。它与既有纪律同源（SKILL 接续核对、prove 证据推翻完成结论即改回），只是把核对触发点扩展到每次汇报、且用用户侧视角。升级触发器：若「总结与检查点不一致」成为反复出现的漂移信号，再考虑让 check_work 或宿主侧做这个对照（机械门），现在不加规则。memory 写入的汇报归属在 memory-direction.md（汇报写了/更新了哪条长期判断、依据、复核时机），SKILL 汇报段不复述；「做了什么」自然包含沉淀内容，无需单独命令。

### 完成写入的机械咬合

完成门「全过 + gap 空才 complete」长期靠模型自觉手写 status，Greeting 证明这条散文挡不住：值域规则在上下文里、check_work 能拒非法值，但模型既写错值（done）又没调用校验器。校验器存在 ≠ 校验器被触发。修法不是再加一句「收尾必须跑 check_work」（规则已在 SKILL.md，仍被绕过），而是把「写 complete」这个动作本身收归校验器：`check_work.py --close {slug}` 先核对完成门，通过才由脚本写入 complete，不通过拒绝并保持文件原状。模型要做的从「写对状态值」变成「调用一个命令」，后者是更可靠的默认行为；盘上非法值在完成门满足时被该命令自然覆盖，不需要先手写一个合法值（那会重新引入手写出错的机会）。

调研对照（2026-11-18）：v1 把 `check_open_issues.py` 绑在提交链第 4 步（校验是动作的固定一环，不是事后想起）；openspec 的 archive 是 CLI 命令、内置 status 检查；superpowers `verification-before-completion` 的 Iron Law 要求每条完成声明都有「这条消息里刚跑出的证据」，连「Done!」语气词都算违规；pstack 根本没有「关闭」动作，完成=真实产物验证 + 独立验证者判 PASS（作者不能自判）；spec-kit 逐任务勾 `[X]` + 尾部完成 checklist。共同点：完成不靠「模型觉得自己做完了」，而靠一个外在于模型自觉的机械前置。bw 的「做完自动收口」意图本身可行（pstack/superpowers 证明无显式关闭可行），缺的是完成写入的机械前置；--close 补的就是这一环，而非回到 v1 的用户授权显式关闭。

适用边界：完成命令只能核验记录中的条件，不能保证任务确实做完、证据真实或验收项登记完整。命令存在也不代表模型会调用；仍需审查真实动作与原始要求。当前完成与流转方式见 [收尾](../../../skills/bw/references/close.md)。

### 收尾总结写给要据此行动的人

用户决定（2026-11-18）：每次回复末尾给一个固定收尾总结，用平实语言讲清「做了什么 / 下一步 / 需要你」，让用户不读前面的技术细节也能掌握全局。起因是用户真实使用的痛点——回来面对一堆技术细节看不懂，总得再问「下一步是什么 / 需要我做什么」。本质是 bw 把当前状态存在 work 的 current_unit/next_action 里供 agent 接续，但没稳定浮到给用户的回复里。「需要你」一栏是核心：集中列等用户拍板、授权、支持或缺信息的内容，没有写「无」，让用户一眼知道哪些事该自己管。两条边界：精炼简洁但不硬限字数（几小时的工作一两句话总结不了，标准是读一遍就懂，不是字数）；「老板/助理」只是用户方便理解的比喻，不进提示词，提示词用中性表述。由 SKILL.md 汇报段统一承载；与 work 模板的「需要用户看的推断或无法判定」是不同载体（回复 vs 落盘文档），语义一致不矛盾。

后续补强与模板收敛：「需要你」每项带推荐+一句理由（消除提问轮次带推荐而需要你不带推荐的盲区）。针对「回复没章法、没重点、看着累」，固定输出模板为：做了什么=一句总领起头+无序列表列全要点，下一步=有序列表，需要你=有序列表+每项带推荐。措辞教训：凡可能被读成数量限制的措辞（「一句话」「核心一件」）都要换成显式说明结构（「一句总领起头，列表列全」）。2026-11-19 复盘实证：1.0.2 把收尾总结拆成 SKILL.md 汇报段的三行「`- **标签**：…`」单行键值列表和 writing.md「收尾总结」节的散文列表描述两半，结果模型直接照抄 SKILL.md 的三行单行形状，忽略了 writing.md 的结构（且每次回复都触发的总结被放进了按需才读的 reference）。修法是把收尾总结的可视模板合并回唯一权威位置 SKILL.md 汇报段，删掉 writing.md 的重复小节——凡要求固定排版结构的输出，直接在触发点给可视模板，不用散文描述列表形状，更不在两处各写一半。

## 收益和代价

评测宿主、事件格式、隔离方式、输入或验收改变时重新核对可比性；新增行为承诺时补对应场景，不能沿用相邻样例的通过结论。

## 备选方案

- **备选方案 A：以大型任务单次运行全绿作为交付门，每次失败都补一条针对性规则**。最强理由是直观回应眼前失败；但实测表明高难任务失败点随模型方差移动，逐轮加规则只会把技能重新养胖而无法消除方差，故改用安装技能 vs 不装技能的 A/B 交替对照通过率。
- **备选方案 B：只看最终产物与业务测试退出码，不审查工具轨迹与真实会话原文**。最强理由是省去过程审查成本；但最终产物全绿无法暴露过程绕路、状态造假或压缩后失忆，故坚持独立审查工具轨迹与真实会话导出原文。
